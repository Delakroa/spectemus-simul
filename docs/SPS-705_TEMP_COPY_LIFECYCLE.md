# SPS-705 — жизненный цикл временной копии

## Цель

Подготовленная копия должна исчезать тогда и только тогда, когда она больше не
нужна. Прогон фазы 0 прямо проверяет пункт «временная копия удалена после
сессии», а копия двухчасового фильма занимает около 5,5 ГБ — поэтому ошибки в
обе стороны одинаково дороги: лишнее удаление стоит десятков минут повторной
подготовки, а забытый файл забивает том ноутбука.

Третий тикет из P1 category-B, закрывает четыре пункта: B3, B4, B5, B6.

## Что было

**Свип удалял живую копию (B3) и был недостижим после сбоя (B6).**
`clearNormalizedMediaDirectory` вызывался внутри `startDesktopHost`, то есть при
каждом старте рантайма — включая кнопку «Перезапустить», доступную прямо во время
сессии. Клик при икоте LiveKit уничтожал копию, которую сессия в этот момент
отдавала гостю. При этом свип стоял после `resolveLanAddress` и
`assertDesktopResources`: если падал выбор LAN-адреса (Mac с Wi-Fi и Ethernet) или
проверка сайдкаров, до него не доходило, и копия после аварийного завершения жила
неограниченно долго.

**Перезагрузка страницы «сиротила» запись (B4).** Освободить запись мог только
renderer по своему `id`. Полная навигация не выполняет React-cleanup, так что
после перезагрузки `id` терялся, а запись и файл оставались. Следующий выбор файла
создавал вторую копию, и обе жили до выхода из приложения.

**Ошибка удаления терялась (B5).** `release` удалял запись из карты и вызывал `rm`,
не обрабатывая отказ. На Windows удаление файла с открытым хендлом падает
`EPERM`/`EBUSY`, и приложение рапортовало об успешной очистке, оставив копию на
диске.

## Изменения

- Свип перенесён в начало `app.whenReady()`, до старта host, в собственный
  try/catch. Он выполняется один раз за запуск приложения и зависит только от
  `app.getPath("temp")`. Рестарт рантайма больше не трогает готовую копию, а
  копия после аварийного завершения подметается при следующем запуске независимо
  от того, чем закончится старт host.
- `registerSource` освобождает прежние записи: host смотрит один фильм за раз,
  поэтому две копии не могут сосуществовать даже после перезагрузки страницы.
- `release` сообщает о неудачном удалении вместо молчания. Запись всё равно
  освобождается, а файл подметёт свип при следующем запуске — каталог временных
  копий очищается целиком.

## Проверка

```bash
node --test desktop/src/main/*.test.mjs
```

Локально: desktop 47/47 (два новых теста).

Оба новых теста проверены откатом: без освобождения прежних записей падает «не
копит копии, если renderer потерял свой id», без обработки отказа — «переживает
сбой удаления временной копии».

## Граница задачи

Освобождение по событиям навигации renderer-а намеренно не добавлялось:
`startDesktopHost` сам выполняет `loadURL`, поэтому такой обработчик удалял бы
готовую копию при каждом рестарте рантайма — то есть возвращал бы дефект B3 через
другую дверь. Ограничение одной активной записью решает ту же задачу, не завися
от источника навигации.

ffmpeg по-прежнему не регистрируется как owned process: аварийное завершение во
время подготовки может оставить недописанный файл до следующего запуска. Это
отдельный пункт про процессы, а не про жизненный цикл записи.
