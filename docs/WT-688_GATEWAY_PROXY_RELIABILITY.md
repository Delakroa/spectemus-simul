# WT-688 — устойчивость desktop gateway при обрывах proxy-соединений

## Цель

Не оставлять зависшие backend-соединения после того, как пользователь закрыл
страницу или начал новую перемотку, и не повреждать уже установленный
WebSocket-туннель служебным HTTP-ответом.

## Что сделано

- HTTP proxy теперь отменяет запрос и поток ответа к backend, когда клиент
  отключился до завершения ответа. Это освобождает сокет и останавливает
  ненужную передачу данных.
- Передача ответа backend выполняется через `pipeline`: ошибка или обрыв с
  любой стороны корректно закрывает вторую сторону, а не оставляет поток
  работать в фоне.
- У WebSocket proxy появился тот же 15-секундный timeout, что и у HTTP proxy.
- Пока backend ещё не начал ответ на WebSocket upgrade, gateway отдаёт обычный
  `502 Bad Gateway`. После первого байта backend-ответа gateway только
  закрывает туннель: нельзя записывать HTTP 502 после `101 Switching Protocols`.

## Почему это важно

Во время просмотра браузер часто отменяет старые запросы при навигации,
перезагрузке и смене состояния страницы. Без отмены gateway продолжал бы
получать данные от backend для уже ушедшего клиента. А HTTP-строка внутри
открытого WebSocket превращает протокол в повреждённый поток и мешает room
reconnect.

## Проверки

```bash
pnpm --dir desktop test
pnpm check:ci
```

Regression-тесты воспроизводят reset backend-а сразу после `101 Switching
Protocols` и обрыв HTTP-клиента во время бесконечного ответа backend-а.

## Граница

Это надёжность локального desktop gateway, который соединяет LAN-клиента с
loopback backend-ом host-а. Публичный Internet mode потребует отдельного
edge-proxy, TLS и авторизации; этот тикет их не добавляет.
