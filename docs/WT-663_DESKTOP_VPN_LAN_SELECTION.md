# WT-663 — выбор LAN-адреса при активном VPN

## Проблема

Desktop host отказывался запускаться на macOS, когда одновременно были доступны
обычный домашний адрес `en0` и VPN-туннель `utun`. Оба адреса могли быть
private IPv4, поэтому приложение ошибочно показывало техническое требование
перезапуска с `SPECTEMUS_LAN_IP`.

Пользователь готовой preview-сборки не должен знать имена интерфейсов или
задавать переменные окружения, если домашняя сеть однозначна.

## Решение

- `utunN`, `tunN`, `tapN`, `pppN`, IPsec, WireGuard, Tailscale, ZeroTier и
  интерфейсы с VPN в имени считаются виртуальными, как Docker/VM/WSL.
- Такие адреса не участвуют в автоматическом выборе LAN-адреса host-а.
- Если после исключения виртуальных сетей остаётся один физический private
  IPv4, desktop host запускается с ним автоматически.
- Явный `SPECTEMUS_LAN_IP` остаётся только для developer-сценария, где
  действительно доступно несколько физических локальных сетей.

## Проверка

```bash
pnpm --dir desktop test
```

Регрессионный тест воспроизводит фактическую конфигурацию: `en0` с
`192.168.0.103` и VPN `utun5` с `10.216.4.70`. Выбранным адресом должен быть
только `en0`.

## Ограничение

Определение опирается на имя сетевого интерфейса, которое предоставляет ОС.
Если VPN маскируется под произвольное имя без обычного tunnel/VPN-маркера,
desktop host сохранит безопасное поведение: при двух физических кандидатах он
не будет угадывать и покажет ошибку вместо публикации invite в неверную сеть.
