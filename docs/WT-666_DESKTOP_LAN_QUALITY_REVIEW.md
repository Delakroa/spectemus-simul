# WT-666 — аудит качества desktop/LAN host

## Цель

Проверить desktop host как реальный путь пользователя: выбор домашней сети,
запуск локальных sidecar-процессов, LAN gateway, invite-ссылка и восстановление
после ошибки. Это не расширение в Internet mode и не изменение media pipeline.

## Исправлено

### Выбор сети без Terminal

Если на компьютере несколько физических private IPv4, приложение больше не
просит обычного пользователя перезапускать его с `SPECTEMUS_LAN_IP`. Вместо
этого оно показывает адреса и интерфейсы, уже исключив VPN, туннели, Docker и
другие виртуальные сети. Пользователь выбирает домашнюю сеть прямо в окне
приложения; выбранный адрес всё равно повторно валидируется до запуска
sidecar-процессов.

`SPECTEMUS_LAN_IP` остаётся developer override для автоматизированного запуска
и локальной отладки.

### Аварийное завершение runtime

Если после готовности неожиданно завершился backend или LiveKit, supervisor
теперь закрывает gateway и завершает оставшиеся sidecars. В интерфейсе остаётся
явный статус ошибки и кнопка «Перезапустить». То же действие есть на стартовом
экране, если host вообще не смог запуститься.

Остановка теперь пытается завершить все ресурсы даже если закрытие gateway
вернуло ошибку. Это уменьшает риск занятых портов при следующем запуске.

## Проверенная цепочка

- Gateway сначала занимает `8088`, а при `EADDRINUSE` получает свободный порт
  от ОС. Desktop окно открывает этот фактический порт; frontend строит invite
  от `window.location.origin`, поэтому ссылка и QR содержат тот же порт.
- Gateway передаёт исходный private `Host` в loopback backend. Backend берёт
  адрес из host header только при LAN profile и только если это private IPv4;
  loopback и public host не подменяют настроенный LiveKit URL.
- Backend остаётся на `127.0.0.1`; наружу открываются gateway и LiveKit
  media-порты. LiveKit key/secret остаются в данных установки и не передаются
  renderer-у или invite-ссылке.
- VPN-интерфейсы (`utun`, `tun`, `Tailscale`, `WireGuard` и похожие) не
  участвуют в автоматическом выборе адреса.
- Unit-тесты покрывают fallback gateway, VPN-фильтр, аварийное завершение
  sidecar и cleanup при ошибке gateway.

## Важное ограничение Windows

Старый developer-скрипт firewall открывает TCP `8088`, `7880`, `7881` и UDP
`50000–50100` только для профиля Private. Поэтому если desktop gateway ушёл с
занятого `8088` на динамический порт, этот скрипт **не доказывает**, что гостю
будет доступна invite-ссылка на новом порту.

Мы не расширяем правило до произвольных портов и не запускаем PowerShell с UAC
скрытно: это было бы менее безопасным решением. Перед release нужен отдельный
тикет first-run firewall UX: явное согласие пользователя, только Private
profile и правило для фактически выбранного gateway-порта. До него fallback
проверяется кодом, но на физической Windows-сети должен подтверждаться вручную.

## Как проверить

```bash
pnpm --dir desktop test
pnpm --filter @spectemus-simul/frontend test -- DesktopRuntimeStatus.test.tsx
```

Для физического smoke:

1. На host включить VPN и убедиться, что при одной физической LAN приложение
   запускается без выбора туннеля.
2. При двух физических сетях убедиться, что появляется выбор адреса, а не
   требование открыть Terminal.
3. Занять `8088` сторонним процессом, открыть приложение и проверить, что
   invite содержит другой фактический порт. На Windows отдельно проверить
   доступ guest-а через Private firewall.
4. Во время работы остановить LiveKit или backend, убедиться в появлении
   «Перезапустить» и отсутствии оставшихся gateway/sidecar-процессов.

## Следующий шаг

После реального smoke на Mac и Windows выделить firewall UX в отдельный
тикет. До этого не переносить cloud-hardening задачи вперёд LAN reliability.
