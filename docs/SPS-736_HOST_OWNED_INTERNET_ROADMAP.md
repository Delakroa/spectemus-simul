# SPS-736 — вернуть Internet-план к хосту как серверу

## Почему меняем план

Цель владельца: установить Spectemus Simul на свой Mac или Windows, запустить
комнату у себя, отправить ссылку человеку в другом городе; гость входит через
браузер без установки. Мы реализовали LAN именно с локальными backend и LiveKit,
но последующие Internet-тикеты спроектировали иначе: публичная VM стала
владельцем комнат, аккаунтов и медиасервера. Это не было явно согласовано и
добавило требование купить и обслуживать сервер. Такая архитектура не считается
целевым продолжением продукта.

## Принятое продуктовое требование

- Компьютер host-а создаёт и ведёт комнату, хранит её текущие права и состояние,
  управляет воспроизведением и является источником медиапотока. Оригинал фильма
  и временная копия остаются на компьютере host-а.
- Гость получает ссылку и открывает её в обычном браузере без отдельной
  установки, регистрации, VPN и настройки роутера.
- Пользователю не требуется покупать, разворачивать или администрировать VM,
  домен, PostgreSQL и SMTP ради одной комнаты. Если продукту понадобится
  инфраструктура-посредник, её роль и стоимость должны быть отдельным явным
  решением, а не скрытым условием установки.
- LAN-режим и его ссылка продолжают работать как сейчас. Internet-приглашение
  нельзя подменять LAN-ссылкой, если внешнее соединение не удалось.
- Нельзя просто открыть нынешний LAN gateway/LiveKit портами в интернет:
  текущие LAN-права и HTTP-ссылка для этого не рассчитаны. Внешний вход
  получит отдельную авторизацию и доверенный HTTPS/WSS до первого гостя.

Это **цель**, а не обещание уже работающей функции. Прямое подключение через
домашние NAT/CGNAT и межсетевые экраны нельзя гарантировать для всех. WebRTC
может потребовать signaling для установления соединения и TURN/relay при
невозможности прямого пути. Посредник в таком случае не обязан владеть
комнатой или хранить файл, но передача медиапотока через него имеет стоимость.
Это следует из устройства [WebRTC signaling](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Signaling_and_video_calling)
и [ICE/STUN/TURN](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Protocols),
а не из выбора конкретного облачного поставщика.

## Статус уже написанного кода

| Часть                                                                                                     | Решение сейчас                                                                                                                                             |
| --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| LAN desktop, backend, LiveKit и media pipeline                                                            | Сохраняем без изменений; это работающая основа и источник повторного использования.                                                                        |
| Public `/api/v2` accounts, invites, device binding, central LiveKit, staging VM (WT-654, SPS-716/720–735) | Оставляем в git как завершённый эксперимент, но **не** считаем путём к следующему пользовательскому релизу. Флаги остаются выключены; VM не разворачиваем. |
| Общие UI/media-компоненты Internet-ветки                                                                  | Оцениваем переиспользование после выбора транспорта; не привязываем новый host-owned flow к центральной БД/SMTP по умолчанию.                              |

Не удаляем крупный объём кода до доказательства нового пути. Не включаем старый
public runtime «для проверки», потому что он подтверждал бы другую схему.

## Следующий порядок работы

1. **SPS-737 — сетевой и архитектурный proof.** В отдельном PoC сравнить:
   (а) публикацию уже локальных backend/LiveKit через защищённый путь;
   (б) host-to-browser WebRTC с host-owned room state и минимальным
   rendezvous/signaling; (в) ограниченный relay fallback. Для каждого указать, где живут
   права комнаты, какие порты/домены/настройки нужны, что делает гость и через
   кого реально идут байты фильма. Не переносить production API до вывода.
2. **Решение по соединению.** На Mac host ↔ Windows browser и Windows host ↔ Mac
   browser из двух разных домашних сетей доказать первый кадр, звук, паузу,
   перемотку, чат, reconnect и закрытие комнаты. Отдельно проверить сеть без
   входящих соединений/UDP. Зафиксировать direct/relay path, требуемые действия
   пользователя и оценку трафика. Если один клик не получается без relay,
   назвать это прямо и согласовать политику посредника и расходов.
3. **Только после proof — продуктовые тикеты.** Выбрать один транспорт и
   разработать host-owned приглашение, короткоживущую авторизацию гостя,
   браузерный вход и lifecycle/cleanup. Затем интегрированные Mac/Windows
   сборки и матрица разных сетей. Публичный release gate — только после
   физического подтверждения, а не зелёных unit-тестов.

## Граница этого тикета

Только архитектурное решение и документация. Контракты, runtime, installer,
серверы и учётные записи не меняются. Проверка: форматирование документов,
согласованность README/roadmap/исторического ADR и чистый diff. Rollback —
вернуть документированный прежний план, без миграции данных. Риск следующего
этапа: host-owned Internet со ссылкой для браузера может потребовать хотя бы
небольшой внешний сервис; отсутствие обязательной личной VM не означает нулевую
стоимость эксплуатации для продукта.

REST/WebSocket contracts, unit-тесты, миграция данных — N/A: product-код не
меняется.
