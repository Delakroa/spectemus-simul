# WT-686 — устойчивое восстановление playback после reconnect и перезапуска host-а

## Цель

Гость не должен оставаться с устаревшим статусом «Нет состояния», если host
обновил страницу, заново подключился к LiveKit или связь с LiveKit оборвалась на
обеих сторонах. Восстановление должно быть понятным: автоматическим для
краткого reconnect и явным действием для окончательного разрыва.

## Что сделано

- Каждая новая публикация playback state получает уникальный `publisherSessionId`.
  Гость теперь сравнивает revision только внутри одной публикации. Поэтому после
  обновления страницы host-а новое сообщение с `revision: 1` принимается, а
  запоздавшее сообщение старой публикации не может вернуть прежнее состояние.
- Старые клиенты без `publisherSessionId` остаются совместимы: их сообщения
  обрабатываются как одна legacy-публикация.
- `signalReconnecting` из LiveKit показывается как «переподключение», а не как
  нейтральное ожидание. В UI не возникает ложного ощущения, что просмотр уже
  остановлен.
- При terminal `disconnected` пользователь получает понятную ошибку и действие
  «Повторить LiveKit». Оно запрашивает свежий token и создаёт новое подключение.
  Намеренное закрытие комнаты и выход пользователя не показывают это действие.

## Проверки

```bash
pnpm --filter @spectemus-simul/frontend exec vitest run \
  src/features/rooms/playback-state.test.ts \
  src/features/rooms/livekit-connection.test.ts \
  src/features/rooms/use-room-session-host-controls.test.tsx
```

Тесты доказывают, что после restart host-а гость принимает новое состояние с
revision заново, игнорирует запоздавший пакет старой публикации, корректно
показывает signal reconnect и даёт ручной retry при terminal disconnect.

## Граница

Тикет не меняет room lifecycle, протокол backend и безопасность LAN gateway.
Отдельно остаются защита proxy/WebSocket и Internet mode с TLS/TURN и
приглашениями. Это именно стабилизация существующего локального просмотра.
